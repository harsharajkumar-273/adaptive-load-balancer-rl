\title{Admit Tasks, Not Requests: Overload Control for Agentic LLM Workloads}
\author{Anonymous Authors}
\date{}
\begin{document}
\maketitle
\begin{abstract}
Autonomous agents turn one user task into a chain of dependent LLM calls separated by tool calls,
and they retry automatically when a call times out. When offered load exceeds capacity, a server that admits work
per \emph{request} spends most of its time on steps of tasks that never finish: with task lengths and tool times resampled from real
coding-agent sessions, goodput at 2.4$\times$ overload is 0.21 of capacity with no admission control and 0.61 with per-request load shedding,
and 81\% (no control) and 41\% (shedding) of server time is wasted. Admitting per \emph{task}, the idea of session-based admission control for web servers,
avoids this. For agents we add a closed-population fluid result: with $N$ admitted tasks, $C$ slots, step time $s$ and tool time $\tau$, the queueing wait is
$\max(0,Ns/C-s-\tau)$, so capping $N$ at $C(s+\tau+D)/s$ holds the wait at a target $D$ whatever the offered load, using only online estimates of $s$ and $\tau$ and no length
information. With $D$ set to a tenth of the client timeout, this cap holds 0.92--0.94 of capacity from 1.2$\times$ to 4$\times$ overload on trace-calibrated tasks (1.01--1.04 on synthetic ones)
with no task lost mid-way, and without per-regime tuning it is within 0.9 of the best policy in 67\% of 18 trace-calibrated and 85\% of 81 synthetic regimes. It is weak when KV memory is the binding constraint,
where per-request shedding can win. Length-aware admission completes up to 2.3$\times$ more tasks but starves long ones (0\% of long tasks complete at 4$\times$ load).
All results are simulations of one server.
\end{abstract}

\section{Introduction}
Agentic workloads differ from chat in two ways that matter under overload. A task is a chain of LLM calls whose
prompts grow, so abandoning a task midway throws away all the work already done on it, and its KV state must be
kept or rebuilt between calls. And clients retry on timeout without a human to stop them, so an overloaded server sees more
work exactly when it is slowest, the feedback loop behind metastable failures~\citep{bronson2021metastable,huang2022metastable}.
Agent-serving systems schedule and cache around tool calls, for example by pinning KV state for a time-to-live, prioritising program
progress, or routing by session~\citep{continuum2025,tokencake2025,saga2026,cachewise2026,smetric2026,talaria2026}; admission under overload is
only proposed in open issues of serving projects (e.g.\ session-level admission control in llm-d) and, for web servers, was studied as session-based admission control~\citep{cherkasova2002sbac}.

We ask: \emph{when agents run multi-step tasks and retry automatically, how much does admitting per task instead of per request help as offered load grows past capacity, what rule achieves it without tuning, and when does it fail?}
Contributions:
\begin{enumerate}
\item \textbf{A model and a failure.} An agent-overload simulator (multi-step tasks, tool calls, KV eviction, timeouts, retries, task identification and length-knowledge levels), run both with synthetic distributions and with task lengths and tool times resampled from real coding-agent sessions~\citep{tracelab2026}. Without task-level admission goodput collapses and most server time is wasted (\cref{sec:overload}).
\item \textbf{A closed-population result and a tuning-light rule.} Little's law on the cycle of a task gives the wait $\max(0,Ns/C-s-\tau)$, hence a cap on admitted tasks that fixes the wait at a target (\cref{sec:theory}). Its safety depends on counting tasks, not on length predictions.
\item \textbf{Evidence on robustness, and on limits.} The rule is insensitive to its parameter once expressed relative to the client timeout, matches tuned alternatives in most regimes, and shows two costs of the alternatives: length-aware admission starves long tasks and, on real heavy-tailed lengths, wastes capacity; and the rule is conservative when KV memory binds (\cref{sec:eval}).
\end{enumerate}
We do not claim that delay-targeted concurrency limits~\citep{welsh2001seda,zhou2018dagor,cho2020breakwater,netflixconcurrency} or session admission~\citep{cherkasova2002sbac} are new; the contribution is their analysis and evaluation for agentic LLM workloads.

\section{Model}
\paragraph{Server.} $C{=}16$ parallel slots (a batching engine abstracted to $C$ concurrent steps), step time lognormal with mean $s{=}2$\,s (CV 0.5). KV memory holds $K$ tasks (default 64); the least recently used task not in service is evicted when full, and a step whose KV was evicted pays an extra $0.25\cdot(\text{steps done})\cdot s$ to rebuild it.
\paragraph{Tasks.} Tasks arrive as a Poisson process. In \emph{synthetic} runs a task has $1+\text{Geom}$ steps with mean 6 and tool times are exponential with mean 3\,s. In \emph{trace-calibrated} runs, task lengths (rounds per turn, clipped to 100; mean 9.0) and tool times (wall latency of tool calls, clipped to 300\,s; mean 6.9\,s, median 0.2\,s) are resampled from the public TraceLab dataset of Claude Code and Codex sessions (32{,}341 turns, 743{,}050 tool calls)~\citep{tracelab2026}, which is very heavy-tailed. \emph{Load} is the task arrival rate over the no-failure task capacity $C/(s\,\mathbb{E}L)$.
\paragraph{Clients.} A step times out after $\theta{=}30$\,s; if still queued it is cancelled, if in service it completes and is wasted. The client retries with exponential backoff (base 2\,s, jitter) at most 3 times, then the task is lost with all its work. Goodput is completed steps over step capacity; we also report tasks lost mid-way and wasted server time.
\paragraph{Policies.} \emph{none}: admit everything, FIFO. \emph{prog}: serve requests of tasks with more progress first (program-level FCFS). \emph{shed}: reject a step when the queue exceeds $Q$. \emph{cap}: admit a new task while fewer than $N$ are admitted. \emph{work budget}: admit a new task if the estimated remaining work of all admitted tasks plus the new one fits in $H$ seconds of capacity, with the task's length known exactly (\emph{oracle}), noisily (\emph{pred}), or replaced by the mean. \emph{Little's-law cap}: below. Task-level policies must identify which task a step belongs to; we model a tag (always recognised) and inference that recognises a step with probability $p$ (otherwise the step is treated as a new task and can be refused mid-task).

\section{A Closed-Population Result}\label{sec:theory}
Admitted tasks form a closed population: each alternates between a tool phase (no server) and a step (queue plus service).
\begin{proposition}\label{prop:wait}
Let $N$ tasks cycle through a tool phase of mean $\tau$ and a step of mean service $s$ on $C$ slots. In the fluid limit the throughput is $X=\min(C/s,\,N/(s+\tau))$ steps per second and the mean queueing wait is $W=\max(0,\;Ns/C-s-\tau)$.
\end{proposition}
\begin{proof}[Sketch]
Little's law on the cycle gives $N=X\,(s+\tau+W)$. If the slots are not saturated, $W=0$ and $X=N/(s+\tau)$. Otherwise $X=C/s$ and solving for $W$ gives the stated value.
\end{proof}
\textbf{Rule.} Admit a new task only while $N<C\,(\hat s+\hat\tau+D)/\hat s$, where $\hat s$ is the measured mean step time (including KV rebuilds, and including steps whose client gave up, which the server still runs; measuring only completed steps biases $\hat s$ low under overload and inflates the cap), $\hat\tau$ is the measured gap between a task's step finishing and its next step arriving, and $N$ never exceeds the KV capacity $K$. Then $W=D$ when the server is saturated, independently of the offered load. If $D$ plus the variability of waits stays below the timeout $\theta$, steps rarely time out: no retries, no wasted work, and admitted tasks complete. We therefore set $D=0.1\,\theta$; a fixed $D{=}5$\,s works for $\theta{=}30$\,s but fails for $\theta{=}15$\,s on heavy-tailed trace tasks (73\% of tasks lost in one regime), because the wait distribution then crosses the timeout. Estimation errors in task \emph{lengths} do not affect safety, because the rule counts tasks and uses no length; lengths only change which tasks are admitted.

\subsection{Overload}\label{sec:overload}
\begin{figure*}[t]\centering
  \includegraphics[width=\textwidth]{figA7_trace_overload.png}
  \caption{Trace-calibrated tasks, $K{=}64$: goodput, tasks lost mid-way and wasted server time against offered load.}
  \label{fig:overload}
\end{figure*}
\Cref{fig:overload} uses task lengths and tool times from real agent sessions. Without admission control goodput falls from 0.88 at 0.9$\times$ to 0.41 at 1.2$\times$ and 0.21 at 2.4$\times$; 71\% of tasks are lost mid-way and 81\% of server time is wasted. Serving by progress is worse at high load (0.18 at 2.4$\times$). Per-request shedding ($Q{=}16$) keeps 0.61 at 2.4$\times$ and 0.57 at 4$\times$ but still loses 21--25\% of tasks mid-way and wastes 41--48\% of server time, because it refuses steps of tasks it already accepted. A task cap ($N{=}64$) and the Little's-law cap hold 0.92--0.94 from 1.2$\times$ to 4$\times$ with no task lost and about 1\% of server time wasted; the work budget ($H{=}20$\,s) holds 0.87--0.89. The price is refusing new tasks at the door: at 4$\times$ only 24\% of arriving tasks complete (against 4\% with no control and 55\% with shedding, which completes more tasks but wastes work).
With synthetic (geometric, exponential) tasks the picture is the same with sharper numbers: no control 0.26 and shedding 0.53 at 2.4$\times$, task-level policies 1.00--1.04, and no task lost mid-way (\cref{fig:sens} shows the full parameter ranges).

\Cref{tab:regimes} summarises. Without tuning, the Little's-law cap matches tuned alternatives at the median and is within 0.9 of the best in 85\% (synthetic) and 67\% (trace) of regimes, whereas the best task cap $N$ varies across regimes (64 in 29, 32 in 23, 128 in 16, 16 in 13) and a single fixed $N$ is far worse (10th percentile 0.62 and 0.49). Its weak regimes are all KV-bound: all 12 synthetic regimes where it falls below 0.85 of the best have a KV capacity of 16 tasks. With real trace tasks and a 16-task KV, per-request shedding is better than every task-level policy (0.36--0.39 against 0.25 for the Little's-law cap at 2.4--4$\times$): when KV memory binds, refusing individual steps keeps more state resident than admitting whole tasks. We tried admitting up to 2$\times$ or 4$\times$ the KV capacity and it was worse overall.

\subsection{What task information is worth}
\begin{figure}[t]\centering
  \includegraphics[width=\columnwidth]{figA5_information.png}
  \caption{Synthetic tasks: work goodput and long-task completion for different knowledge of task length.}
  \label{fig:info}
\end{figure}
Knowing task lengths seems useful: with exact lengths the work budget completes 2.28$\times$ the task capacity in tasks at 4$\times$ load (noisy, $\sigma{=}0.5$: 2.12$\times$), because it admits short tasks. But work goodput is unchanged (1.01--1.03), and long tasks (more than twice the mean) are starved: 0\% (exact) and 3\% (noisy) complete, against 25\% for the length-free cap (\cref{fig:info}). Length information buys a count of completed tasks, not capacity, at the cost of fairness. On real heavy-tailed lengths it also costs capacity: length-aware admission refuses long tasks even at low load, giving work goodput of only 0.26--0.84 (exact lengths) and 0.29--0.91 (noisy), against 0.58--0.94 for the length-free caps from 0.6$\times$ to 4$\times$.
Task identity matters more with real tasks: recognising 70\% of steps loses 2\% of goodput at 4$\times$ on synthetic tasks but 15\% on trace-calibrated ones (0.79 against 0.93), since heavy-tailed tasks have more steps that can be refused mid-task.

\subsection{Surges and retries}
After a 60\,s surge of 3$\times$ and 5$\times$ a base load of 0.8, only the unprotected server stays degraded (55\% and 60\% of later tasks complete), against 100\% for the default setting of each protected policy (serving by progress: 94\% after a 5$\times$ surge; a badly tuned queue limit $Q{=}64$ or cap $N{=}16$: 75\% and 55\%). Per-request shedding with a tight limit also recovers in our model, so this test separates only unprotected from protected servers. A retry sweep is in the artifact summary.

\section{Related Work}
Overload control for services is a mature area: SEDA bounds queues per stage~\citep{welsh2001seda}, DAGOR sheds load by priority from queueing time~\citep{zhou2018dagor}, Breakwater issues server credits driven by queueing delay~\citep{cho2020breakwater}, and Netflix's concurrency-limits library adapts a limit with Vegas- and gradient-style rules~\citep{netflixconcurrency}. Session-based admission control, which refuses new web sessions to avoid aborting long ones, addresses the same waste for e-commerce~\citep{cherkasova2002sbac}. Metastable failures from retry amplification are documented in production~\citep{bronson2021metastable,huang2022metastable}. Our rule is in this family; what is specific here is the closed-population formula that accounts for tool time and measures service time on abandoned work, the KV bound, the length-information analysis, and the evaluation on real agent task distributions. Agent-serving systems reduce latency by pinning or prefetching KV state, prioritising program progress and routing by session~\citep{continuum2025,tokencake2025,saga2026,cachewise2026,smetric2026,talaria2026}; they target throughput and completion time, not refusing work under overload, and \emph{prog} in our evaluation is a minimal version of their scheduling idea. TraceLab characterises coding-agent workloads and provides the distributions we resample~\citep{tracelab2026}.

\section{Limitations}\label{sec:limits}
All results come from one simulated server: no real GPU, batching or decode model. Task lengths and tool times in the trace-calibrated runs are resampled independently from coding-agent sessions, which loses correlations (e.g.\ between a task's steps), and the empirical lengths are clipped at 100 steps and 300\,s tool calls; other agent types (web, customer-service) may differ. Arrivals are Poisson. We do not model priorities, deadlines or multiple replicas; with many routers the admission state would itself be shared, stale state, the setting of a companion study on herding. The Little's-law cap needs task identity to count tasks and measure $\tau$, assumes the client timeout is known, and is conservative when KV memory binds, where shedding can be better. The parameter $D/\theta=0.1$ was chosen after a failure with a fixed $D$ and is validated on the same simulator, not an independent system. The recovery experiment does not separate good protected policies. There is no real-system measurement yet.

\section{Conclusion}
Under overload, agents make admission a per-task decision: a refused task costs nothing, an abandoned one wastes everything. Counting admitted tasks against a Little's-law cap holds the queueing wait at a fraction of the client timeout, keeps goodput near capacity on synthetic and real task distributions, and needs neither length prediction nor per-regime tuning, but it relies on knowing which request belongs to which task and on KV memory not being the binding constraint.
